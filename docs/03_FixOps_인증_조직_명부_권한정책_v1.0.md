# FixOps v1.0 — 회원가입·조직·단지·명부·RBAC 정책

> **상태:** v1.0 설계 승인 후보 — 사용자 승인 정책 24개 및 권장 추가 쟁점 6개 반영. 실행·통합 테스트 전이며 코드 반영을 의미하지 않음.  
> **기준:** 2026-11-18 / 최종 발표 2026-12-21 / 5명·20영업일 / `OZA-bot-droid/fixops` main/docs v0.5~v0.5.4  
> **우선순위:** P0=시연 핵심 구현, P1=여력 시, P2=후속 확장.

## 1. 인증·인가 원칙

**계정 인증 ≠ 조직 소속 ≠ 단지 접근 ≠ 세대 소속 ≠ 리소스 조작 권한.** 다섯 층을 나누어 서버에서 매 요청 검증한다. 가입자는 공개 회원가입 시 권한·조직 ADMIN을 임의 선택할 수 없다.

| 신원 | 역할 | 허용 범위 |
|---|---|---|
| PLATFORM_ADMIN | 전역 운영자 | 조직 신청·관리권 이전·예외 승인. 주민 민감 데이터 자동 열람 불가 |
| ADMIN | 조직별 관리자 | 소속 조직의 **승인된 단지 범위** 내 구성원·시설·작업·재고 관리 |
| TECHNICIAN | 조직별 작업자 | 해당 단지에서 배정된 작업·일정 및 허용된 재고 사용 |
| USER | 조직별 일반 회원 | 승인된 세대·자신의 신고·허용된 공용 정보 |
| 미가입/소속대기 | 인증된 계정 | 조직 검색·신청/승인 상태 조회만 가능 |

## 2. 최초 관리자 및 조직 생성

1. PLATFORM_ADMIN 초기 계정은 배포 초기 시드/관리자 명령으로 생성; 공개 회원가입에서 전역 권한 획득 불가.
2. 계정 이메일 검증 후 `POST /api/organizations`로 조직 생성 신청(`PENDING_APPROVAL`).
3. BUILDING의 경우 K-apt에서 선택한 `kapt_code`를 **서버에서 재조회**하고 주소·기존 활성/대기 등록과 대조. 없으면 `MANUAL_REVIEW`.
4. FACTORY는 사업자등록 API 없음; 조직명·책임자 연락수단·승인 요청을 플랫폼 운영자가 심사(객관적 소속 확인을 자동 보증하는 구조 아님).
5. PLATFORM_ADMIN이 승인 시 Organization ACTIVE + 신청자 첫 ADMIN ACTIVE를 **같은 Member DB 트랜잭션**에 저장; 마지막 ADMIN 강등/탈퇴 차단.
6. 하나의 단지에 활성 관리 조직은 1개만. 관리권 변경은 시작/종료 시점을 남기고 구 조직 단지권한 회수.

## 3. 단지 식별과 권한의 분리

- K-apt API 제공 예: https://www.data.go.kr/data/15057332/openapi.do / https://www.data.go.kr/data/15058453/openapi.do
- `kaptCode`가 동일하면 중복 후보 확정; 이름/주소 일치 여부는 보조 정보. 결과 없음은 단지 부재 증거 아님.
- 같은 주소에 복수 단지 존재 가능; 주소만으로 자동 병합 금지.
- `apartment_complex.id`는 물리 단지의 내부 ID; `organization.id`는 관리 주체.
- `member_complex_access`를 통해 조직 구성원의 접근 가능한 단지를 서버에서 판정.
- 거주자 `resident_unit.location_id`는 Asset 서비스의 UNIT 위치여야 하며 `complex_id` 범위 일치 확인.

## 4. XLSX 명부 등록

### 4.1 표준 입력

`동`, `호`, `성명`, `연락처`, `입주상태`, 선택 `입주일`, `퇴거일`. 대표자 생년월일·주민등록번호를 기본 항목으로 받지 않는다.

- `.xlsx` P0; `.xls`, 임의 컬럼 매핑 P1.
- 업로드 ADMIN만 가능; MIME·시그니처·압축해제 크기·시트/행/열 제한, 수식·매크로 거부.
- `upload→STAGING→PREVIEW→COMMIT→COMPLETE`. `import_job_id` 중복 커밋 방지.
- 전체 교체/부분 갱신을 명시 선택. 명부 누락만으로 즉시 퇴거 처리 금지.
- `file_sha256`/반영 대상 버전으로 중복 및 동시 업로드 충돌 탐지.
- 정상/오류 행별 보고 및 미리보기. 실패 시 부분 성공의 범위를 명시하고, 데이터 손상 없이 재시도.
- 실제 도입 전 명부의 별도 서비스 처리·제공에 대한 적법 근거와 동의/고지·위탁 관계를 검토해야 함.

### 4.2 연락처 보호

- 연락처 원문은 암호화, 비교 인덱스는 키 기반 HMAC(단순 SHA-256 금지).
- 원본 파일은 임시 S3 비공개 저장, 처리 완료 후 보존 정책에 따라 삭제.
- 로그/Trace/LLM 입력에 연락처·원본 명부 데이터를 포함하지 않음.

## 5. 주민 계정 생성·세대 연결

2026-11-25 변경: Gmail SMTP 계정 이메일 인증과 주민 거주 확인을 분리한다. 등록 코드를 기본으로 하고 SMS는 선택적으로 활성화한다. 구현 기준은 fixopsdev 작업 브랜치이며 팀 승인 및 통합 검증은 별도이다.

1. 일반 계정 생성 후 이메일 소유 검증. SMTP는 `VERIFICATION_EMAIL_PROVIDER=smtp` 설정으로 활성화한다.
2. 주민은 활성 명부가 있는 단지를 선택한다.
3. 기본 방식: 관리 단지 ADMIN이 본인·거주 자격을 확인한 뒤 활성 명부 항목에 일회용 등록 코드를 발급한다. 128비트 난수(32자리 16진수), 유효기간 24시간, 원문은 발급 응답에서만 표시하고 DB에는 도메인 분리 HMAC만 보관한다.
4. 선택 방식: `VERIFICATION_SMS_PROVIDER` 활성화 시 연락처 OTP 및 동·호·명부 HMAC 일치 검증을 제공한다. 비활성화 또는 인증 방식 조회 실패 시 화면에서 SMS를 숨긴다.
5. 검증된 증명, 활성 관리관계·명부, 미연결 항목, Asset UNIT 및 호환 조직 소속을 확인하여 자동 연결한다. 연결 조건 미충족 시 심사 대기 또는 계약 오류로 처리하며 관리자도 증명·명부 검증을 우회할 수 없다.
6. 동일 명부 항목에 인증 방식과 무관하게 심사 대기 중복을 제한한다. 동일 세대의 별도 명부 항목은 각각 가입 가능하다.
7. 등록 코드 재발급은 기존 미사용 코드를 회수한다. 사용 완료 코드는 재사용 불가. 계정별 15분 동안 실패 5회 제한을 적용한다. 코드 발급·회수 권한은 해당 단지 ADMIN으로 제한한다.
8. 명시적 퇴거 시 미사용 코드 회수, 인증 대기/심사 대기 신청 반려, 관련 OTP 무효화, 기존 세대 권한 회수 및 세션 무효화를 수행한다. 재입주 시 이전 신청을 복구하지 않는다.
9. 코드·OTP 원문을 로그·감사·Trace에 남기지 않는다. 감사 대상은 등록 코드와 주민 신청을 구분한다.

**주의:** 등록 코드는 관리자의 사전 본인 확인에 의존하며 SMS는 전화번호 통제만 확인한다. 어느 방식도 독립적인 공적 거주 증명은 아니다. 실운영에서는 관리자의 본인 확인 및 코드 전달 절차를 별도로 수립한다.

## 6. 시연 Mock

- `VERIFICATION_EMAIL_PROVIDER=mock` 또는 `VERIFICATION_SMS_PROVIDER=mock`는 데모 프로파일 및 **허용된 가상 계정/연락처**에서만 작동; 운영 프로파일은 mock 값이면 시작 실패.
- K-apt 장애 시 가상 단지 목록/재현 데이터 사용, 사용자 화면에 데모 데이터임을 명시.
- Excel 2,000행 가상 데이터를 제공하되 식별 가능한 실제 주민 개인정보 금지.
- JWT 서명·조직/세대 권한·재고/예약 DB 제약은 **Mock 금지**.

## 7. JWT·보안 계약

- Access 15분 권장, Member RSA 개인키 발급, Gateway·업무 서비스가 공개키 검증.
- `sub`, `iss`, `aud`, `exp`, `iat`, `org_id`, `membership_id`, `role`를 서버 확인 후 발급. 다중 단지 스코프는 보안 DB 확인 또는 안전하게 관리된 claim으로 제한.
- 프로필/역할/소속/세대 변경 후 Refresh Session 회수, Access 만료 전에 민감 API는 최신 상태 검증.
- 사용자 직접 제출 `X-Member-Id`, `X-User-Role`, `X-Org-Id` 제거. 내부 호출도 서명된 위임 컨텍스트와 서비스 신원을 검증.
- 비밀번호는 안전한 단방향 해시. 로그인·OTP·가입·K-apt 조회에 요청 제한.
- ALB/Gateway/Member 로그·Trace에 JWT, 인증코드, 이름·연락처 원문 노출 금지.

## 9. 감사·동의·파기

- 권한 변경, 조직 개설 승인, 명부 import 확정, 세대 자동 연결/거절, 퇴거, 관리권 이전은 `actor`, `scope`, `before/after`, `occurred_at` 기록.
- 개인정보 처리 목적·보유기간·삭제 요청·백업 복구 시 파기 정책은 실제 서비스 도입 전 확정. 본 프로젝트는 시연 목적 가상 정보만 사용.
- AI 외부 제공자의 데이터 처리/국외 전송 여부·학습 사용 여부를 제공자 약관과 사용 설정으로 검토; 민감 민원 원문 전송 지양.


## 조직 개설 Onboarding 보완 정책 (2026-11-26)
- 일반 USER/TECHNICIAN만 보유한 계정은 직접 개설 신청 불가. 미소속 또는 별도 ADMIN 소속이 있는 이메일 인증 회원은 서비스 도입 신청 가능. PLATFORM_ADMIN은 초대·심사를 담당한다.
- 일반 신청은 기존 승인 절차 유지. 신청자당 심사 대기 조직 1건.
- 플랫폼 관리자 초대는 사전 확정 조직명/유형 및 인증된 수신 이메일에 귀속하며 72시간 유효, 일회 수락·회수 가능. 비밀 코드 복사 없이 로그인 후 내 초대 목록에서 수락한다. SMTP는 초대 안내 수단이며 실패해도 초대 목록에서 확인 가능.
- FACTORY 초대 수락 시 활성화 및 최초 ADMIN 지정. BUILDING은 단지 관리권 검증 승인과 동시에 활성화; 검증 생략 금지. 기존 조직 구성원 초대는 별도 기능으로 유지.
- 승인 및 수락은 감사 기록, 활성화 후 세션 회수. 기존 신청과 초대 모두 최신 DB 상태를 확인한다.

- 회원가입의 이용 목적은 화면 이동 힌트로만 처리하며 ROLE을 부여하지 않는다. `FIXOPS_PUBLIC_URL`을 신뢰할 수 있는 프론트엔드 origin으로 설정하면 SMTP 안내에 로그인/초대 확인 링크가 포함된다. 설정하지 않으면 안내만 발송된다.
